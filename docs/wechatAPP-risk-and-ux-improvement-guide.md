# 记事微清单：代码风险与体验优化实施说明

> 用途：供后续在具备微信开发者工具、云开发环境和真机调试条件的开发环境中，交给 Codex 分阶段修改与验证。
>
> 基线：`wechatAPP-main(1).zip`，GitHub 快照提交 `5d983db3f70eba647b59cf2458f15bec2dcb2db0`。
>
> 本文只描述问题、建议和验收标准，不代表相关代码已经修改或完成运行验证。

> 当前状态：本文保留初始快照的问题描述，R-01～R-12 及主要页面优化已经按路线图逐项处理。原文中的“现状”和文件位置用于追溯，不应视为当前实现事实；当前存储策略、实施状态与剩余 UX 项见 `docs/data-storage-strategy.md` 和 `docs/README.md`。

## 1. 项目现状摘要

项目是原生微信小程序，使用 JavaScript、WXML、WXSS 和微信云开发。产品已经由早期的点餐/购物车模型转向“个人与家庭生活清单”：

- 饮食场景：菜谱、今日饮食清单、采购清单、库存、饮食记录。
- 生活场景：生活清单、循环清单、自定义模板、完成记录。
- 回顾场景：月历与本月统计。

数据目前分布在两处：

| 数据 | 存储位置 | 当前同步特性 |
| --- | --- | --- |
| 菜谱 | 云数据库 `dishes` | 全局共享 |
| 今日饮食清单 | 云数据库 `carts` | 按用户 OpenID 隔离，可跨设备 |
| 饮食记录 | 云数据库 `orders` | 按用户 OpenID 隔离，可跨设备 |
| 菜谱收藏 | 本地存储 | 仅当前设备 |
| 食材库存 | 本地存储 | 仅当前设备 |
| 采购勾选状态 | 本地存储 | 仅当前设备 |
| 生活清单及模板 | 本地存储 | 仅当前设备 |
| 生活清单完成历史 | 本地存储，最多 200 条 | 仅当前设备 |

## 2. 优先级定义

| 级别 | 含义 |
| --- | --- |
| P0 | 上线前必须处理，涉及数据安全或破坏性操作 |
| P1 | 应优先处理，可能造成数据不完整、跨设备不一致或明显体验问题 |
| P2 | 建议处理，主要影响维护性、一致性与长期演进 |
| P3 | 清理项，不影响主要功能，可与相关重构一起完成 |

## 3. 风险整改清单

### R-01：菜谱重新初始化接口缺少权限控制（P0）

**位置**

- `cloudfunctions/manageDishes/index.js`
- 云函数入口中的 `action === 'reinit'` 分支

**现状**

`reinit` 会先删除 `dishes` 集合中的旧数据，再重新导入内置菜谱。代码没有校验调用者身份、管理员名单或环境开关。

**影响**

只要客户端能够调用该云函数，就可能构造 `action: 'reinit'` 请求，触发全局菜谱删除和重建。即使内置数据能够恢复，也可能覆盖后台维护的数据，并产生短暂空数据或并发重复数据。

**建议方案**

优先选择以下方案之一：

1. 最稳妥：从面向小程序客户端的云函数中彻底删除 `reinit`，改为仅能从开发脚本或云开发控制台执行的初始化工具。
2. 若必须保留：校验 OpenID 管理员白名单，同时增加仅开发/测试环境可用的开关。
3. 为重建过程增加幂等、事务或版本切换机制，避免“先清空再写入”造成中间态。

**验收标准**

- 普通用户调用 `reinit` 必须失败，且数据库内容不发生变化。
- 未授权调用有明确错误码和日志，不返回模糊的“未知操作”。
- 管理员操作可重复执行，不会产生重复菜谱。
- 正常的 `list` 和 `detail` 不受影响。

**验证建议**

- 使用普通用户 OpenID 调用一次。
- 使用管理员身份调用两次并比较菜谱数量、ID 和内容。
- 在初始化过程中并发调用 `list`，确认不会读到不完整数据。

### R-02：首次读取菜谱时自动初始化存在并发竞争（P1）

**位置**

- `cloudfunctions/manageDishes/index.js`
- `action === 'list'` 且集合为空时的初始化逻辑

**现状**

多个用户在空库状态下同时调用 `list`，都可能判断集合为空并分别插入整套初始数据。

**影响**

可能生成重复菜谱，后续搜索、统计和详情匹配也可能异常。

**建议方案**

- 不在普通查询请求中隐式写入初始化数据。
- 使用独立部署脚本初始化数据库。
- 如果仍需自动初始化，使用固定文档 ID、唯一索引、初始化锁或版本记录确保幂等。

**验收标准**

- 空数据库下并发调用 `list` 后仍只有 20 道菜。
- 每道菜的业务 ID 唯一。
- 查询接口不因初始化失败而返回部分数据。

### R-03：饮食记录查询最多返回 100 条（P1）

**位置**

- `cloudfunctions/manageOrders/index.js`
- `action === 'list'`、`action === 'summary'`
- `pages/orders/orders.js`
- `pages/stats/stats.js`

**现状**

饮食记录列表明确使用 `.limit(100)`；统计查询也没有分页。页面中的日历、本月统计和批量操作均基于一次性返回的数据。

**影响**

长期使用超过 100 条后，旧记录可能消失，统计结果也可能与数据库真实数据不一致。用户不会收到“仅显示部分记录”的提示。

**建议方案**

- 记录列表改为基于 `orderTime` 和 `_id` 的游标分页。
- 月历按日期范围查询，不要为一个月视图拉取全部历史。
- 统计使用云数据库聚合或独立统计接口。
- 明确批量删除只作用于当前筛选结果还是全量数据。

**验收标准**

- 构造超过 120 条记录后可以继续加载并查看全部记录。
- 切换月份只请求对应范围的数据。
- 本月统计与数据库聚合结果一致。
- 分页过程中没有重复或遗漏记录。

### R-04：云端与本地数据边界导致跨设备体验不一致（P1，需先做产品决策）

**位置**

- `utils/favorite.js`
- `utils/inventory.js`
- `utils/shopping.js`
- `utils/life-list.js`

**现状**

饮食清单和饮食记录在云端，收藏、库存、采购状态和全部生活清单在本地。

**影响**

- 更换手机或清除小程序缓存后，本地数据丢失。
- 同一账号在不同设备看到的首页概览和生活清单不同。
- 用户可能误以为所有“记录”都已同步。

**产品决策选项**

1. **全部同步到云端（推荐）**：适合希望长期使用和跨设备同步的产品。
2. **继续本地优先**：界面必须明确标注“仅保存在本机”，并提供导出、导入或备份。
3. **混合方案**：本地草稿、云端正式数据；需要定义同步时机、冲突规则和离线行为。

**推荐实施顺序**

先迁移生活清单与库存，再迁移收藏和采购勾选。为原有本地数据增加一次性迁移流程，不能直接丢弃。

**验收标准**

- 明确形成一份数据存储决策记录。
- 如果改为云同步，两台设备登录同一账号后数据一致。
- 本地旧数据可迁移，重复执行迁移不会产生重复项。
- 网络失败时有清晰状态，不会无提示地覆盖较新的数据。

### R-05：云函数过度信任客户端传入的数据（P1）

**位置**

- `cloudfunctions/manageCart/index.js`
- `cloudfunctions/manageOrders/index.js`
- `utils/cart.js`
- `utils/order.js`

**现状**

加入饮食清单时，客户端传入完整菜品对象；保存饮食记录时，客户端传入菜品、价格、数量等字段。云函数只做少量数量兜底，没有系统校验字段类型、长度、范围及菜谱真实性。

**影响**

虽然当前不是支付系统，但异常客户端仍可写入负数、极大数量、伪造菜品或超长备注，污染记录和统计。遗留价格字段还可能让数据模型继续偏向旧点餐业务。

**建议方案**

- 云函数只接收业务 ID、数量和必要备注。
- 根据菜谱 ID 从云数据库获取可信菜谱快照。
- 对数量、数组长度、字符串长度、状态枚举和批量操作数量设置上限。
- 评估并移除产品不再使用的 `price`、`totalPrice`、`subtotal` 等字段；如果为了兼容旧记录保留，应标注为废弃字段。

**验收标准**

- 非法数量、未知菜谱 ID、空数组和超长备注均被拒绝。
- 错误返回稳定的业务错误码。
- 正常保存、历史展示和“复用这一餐”仍可工作。
- 新旧数据兼容策略有说明和测试。

### R-06：本地存储没有数据版本和迁移机制（P1）

**位置**

- `utils/favorite.js`
- `utils/inventory.js`
- `utils/shopping.js`
- `utils/life-list.js`

**现状**

本地数据直接保存数组或对象，没有 `schemaVersion`。字段变化后只能假设旧数据仍符合最新结构。

**影响**

后续新增重复规则、库存单位或清单字段时，旧用户可能出现渲染错误、统计错误或数据丢失。

**建议方案**

- 为每类本地数据增加版本号。
- 建立逐版本迁移函数，不直接在页面中兼容多个历史结构。
- 迁移前保留备份，迁移失败时回滚并提示。

**验收标准**

- 使用至少两份旧结构样例测试升级。
- 迁移可重复执行且结果一致。
- 不可识别的数据不会导致页面白屏。

---

### R-07：基础库使用 `trial`，构建不可稳定复现（P1）

**位置**

- `project.config.json` 中的 `libVersion`
- `project.private.config.json` 中可能存在的本地覆盖

**现状**

项目使用试验版微信基础库。试验版本变化后，同一份代码可能出现不同编译结果或运行行为。

**建议方案**

- 根据当前线上兼容范围选择并固定稳定基础库版本。
- 记录最低微信版本和基础库要求。
- 在升级基础库时单独提交，并完整回归关键流程。

**验收标准**

- 新环境检出代码后使用相同基础库版本。
- 微信开发者工具无基础库兼容警告。
- 真机覆盖计划中的最低版本和当前主流版本。

---

### R-08：错误处理和可观测性不足（P1）

**位置**

- `pages/home/home.js`
- `pages/cart/cart.js`
- `pages/orders/orders.js`
- 其他包含 `console.error` 的页面
- 三个云函数入口

**现状**

部分失败只写控制台，页面继续显示默认的 0 或空列表。云函数缺少统一异常捕获、错误码和关联日志。

**影响**

用户无法区分“确实没有数据”和“加载失败”，开发者也难以定位具体请求。

**建议方案**

- 统一页面状态：`loading / success / empty / error`。
- 提供重试入口，避免失败时直接呈现空状态。
- 云函数统一包装返回值，记录 action、OpenID 脱敏标识、请求 ID、耗时和错误。
- 避免向用户返回数据库异常原文。

**验收标准**

- 断网和云函数失败时出现错误态与重试按钮。
- 加载失败不会错误显示“0 项”或“暂无记录”。
- 云端可以根据请求 ID 定位一次失败调用。

---

### R-09：缺少统一工程检查和自动化测试（P1）

**现状**

项目根目录没有统一的 `package.json`、Lint、格式化、单元测试或可重复执行的检查命令。当前只能依赖微信开发者工具和人工测试。

**建议方案**

- 增加根目录开发脚本：语法检查、ESLint、JSON 检查、单元测试。
- 优先为纯逻辑模块增加测试：采购量计算、库存到期判断、循环清单刷新、月份统计。
- 为云函数使用模拟数据库或拆分领域逻辑后测试。
- 如果条件允许，引入微信小程序自动化测试覆盖主流程。

**最低验收命令示例**

```bash
npm run lint
npm run test
npm run check
```

具体命令名称可按项目习惯调整，但必须能在干净环境中重复执行。

### R-10：产品术语与旧点餐模型混用（P2）

**位置**

- `utils/cart.js`、`utils/order.js`
- `cloudfunctions/manageCart/`、`cloudfunctions/manageOrders/`
- `pages/cart/`、`pages/orders/`
- 代码注释、变量名及个别弹窗文案

**现状**

用户界面大部分已经改为“今日清单、饮食记录”，但内部仍普遍使用购物车、商品、订单、下单、结算和价格等概念。

**影响**

新功能容易继续沿用错误的领域模型；开发者阅读代码时也可能把产品误解为点餐应用。

**建议方案**

- 先定义术语映射，再分阶段重命名，避免一次性大范围破坏引用。
- 推荐映射：`cart → mealPlan/mealList`，`order → mealRecord`，`food → dish`，`checkout → saveRecord`。
- 云函数名和数据库集合改名需要迁移方案；页面目录可以后处理。
- 删除不再使用的价格、订单状态和批量完成逻辑。

**验收标准**

- 用户可见文案不再出现商品、购物车、订单、下单、结算。
- README、代码注释、函数名和数据字段表达同一个产品模型。
- 旧云数据完成兼容或迁移，不因重命名丢失。

### R-11：仓库和配置文件卫生（P2）

**位置**

- `.env.local`
- `project.private.config.json`
- `.codebuddy/`
- `rules/`
- `codebuddy-plugin/`
- `.gitignore`

**现状**

压缩包包含本地环境配置、私有项目配置以及较多 AI 辅助规则。它们不属于小程序运行代码，但可能增加仓库体积、环境差异和敏感配置误提交风险。

**建议方案**

- 检查 Git 实际跟踪状态，不只依赖 `.gitignore`。
- 使用 `.env.example` 描述必要键名，不提交真实本地配置。
- 明确 AI 规则是团队共享资产还是个人配置；个人配置应排除。
- 在 CI 中增加敏感信息扫描。

**验收标准**

- 新成员可以根据示例文件配置环境。
- 仓库中不存在真实密钥或个人路径。
- GitHub 下载包只包含团队确实需要的规则和源码。

### R-12：遗留和未使用代码（P3）

**位置**

- 未注册页面 `pages/logs/`
- 可能只被旧文档提及的 `utils/util.js`
- 各页面中未使用的价格、状态和旧样式选择器

**建议方案**

通过全局引用检查确认后删除；不要仅凭文件名推断无用。清理应作为独立提交，避免与功能修改混在一起。

**验收标准**

- 删除前后所有注册页面均可打开。
- WXML 事件、导航路径和模块引用检查通过。
- 微信开发者工具不出现缺失文件或未使用资源相关错误。

## 4. 具体体验问题与设计建议

### UX-01：触控目标偏小（P1）

**涉及页面**

- 菜谱页圆形“+”按钮
- 今日清单数量加减按钮
- 日历切换、删除及部分箭头入口

**问题**

多处按钮为 `48rpx` 左右，视觉上清楚，但实际可点击面积偏小，容易误触，尤其是单手使用和较大字体环境。

**建议**

- 视觉图标可以保持原尺寸，但点击容器应扩大到舒适的触控面积。
- 相邻的删除、加减操作需要留出足够间距。
- 为按压状态、禁用状态和请求中状态提供反馈。

**验收标准**

- 真机单手操作时加减、收藏和删除不易误触。
- 连续快速点击不会产生重复提交或数量跳变。

---

### UX-02：固定底栏、固定高度与安全区适配（P1）

**涉及页面**

- `pages/cart/cart.wxss` 的固定保存栏
- `pages/orders/orders.wxss` 的列表高度计算和批量操作栏
- 其他使用 `100vh`、固定底部定位的页面

**问题**

固定高度和 `calc(100vh - ...rpx)` 对不同手机、系统字体、导航栏和全面屏安全区较敏感，可能导致内容被遮挡或出现多余空白。

**建议**

- 使用安全区变量处理底部内边距。
- 尽量让页面自然滚动，减少依赖大段固定高度计算。
- 分别验证有/无原生 tabBar、批量模式、空状态和长列表。

**验收标准**

- iPhone 全面屏和常见 Android 设备底部内容不被遮挡。
- 系统字体放大后仍可滚动到全部操作。
- 键盘弹出时输入框和确认按钮可见。

---

### UX-03：“记录”页面信息过载（P1）

**涉及页面**

- `pages/orders/orders.wxml`
- `pages/orders/orders.wxss`
- `pages/orders/orders.js`

**问题**

同一页面同时承担总统计、月历、生活清单完成记录、饮食记录列表、长按多选和批量删除。首屏较长，用户很难快速判断页面的主要任务。

**建议方向**

可选择以下一种信息架构：

1. 月历作为主视图，选中日期后只显示当天饮食和生活记录。
2. “日历 / 列表”双视图切换，批量管理只放在列表视图。
3. 记录页只负责时间线，本月统计进入独立回顾页。

建议先做低保真原型并真机评估，再改代码。

**验收标准**

- 用户进入页面后能立即理解当前月份、选中日期和当天记录。
- 普通浏览状态不暴露复杂的批量操作。
- 饮食记录与生活完成记录的视觉标识清晰且有图例。

---

### UX-04：缺少统一设计令牌和组件（P2）

**现状**

各页面独立定义颜色、字体、圆角、阴影和卡片样式，存在大量近似但不相同的写法。所有页面 `usingComponents` 均为空。

**建议方案**

建立最小设计系统：

- 色彩：主色、饮食场景色、生活场景色、成功、警告、危险、正文和弱文本。
- 字体：页面标题、分区标题、卡片标题、正文、辅助文字、数字指标。
- 间距：页面边距、卡片内边距、列表间距。
- 圆角与阴影：控制在少量等级。
- 组件：场景卡片、列表项、空状态、错误状态、数量步进器、底部操作栏、确认弹窗入口。

先提取视觉变量，再逐页替换；不要在同一个提交中同时改变交互逻辑。

**验收标准**

- 同类卡片、按钮和状态色在不同页面保持一致。
- 新页面不需要重新复制整套 WXSS。
- 设计系统有简单文档或示例页。

### UX-05：Emoji 图标显示不一致（P2）

**问题**

首页、空状态、统计和功能入口大量使用 Emoji。不同系统的字形、颜色和尺寸差异明显，也不方便统一品牌风格。

**建议**

- 核心导航和高频功能使用一套 SVG/PNG 图标。
- Emoji 可保留在轻量提示或情绪化空状态中，但不要承担唯一的功能识别职责。
- 图标必须有文字标签，不能只靠颜色或形状表达状态。

**验收标准**

- iOS 和 Android 上主要入口视觉一致。
- 图标加载失败时仍能通过文字理解操作。

---

### UX-06：加载、空数据和加载失败容易混淆（P1）

**问题**

部分页面请求失败后仅记录控制台，界面可能继续显示“暂无记录”或数量 0。

**建议**

- 每个异步页面至少设计四种状态：加载中、正常、确实为空、加载失败。
- 首次加载用骨架或轻量加载提示。
- 失败状态提供重试，不覆盖已有缓存数据。
- 保存类操作防止重复点击，并明确成功后的去向。

**验收标准**

- 通过断网和云函数故障测试能看到独立错误态。
- 恢复网络后重试可正常加载。
- 刷新失败时不清空已显示的有效数据。

---

### UX-07：文字对比度和状态表达（P2）

**问题**

多处辅助文字、删除入口使用很浅的灰色；日历又同时依赖橙色填充、蓝色边框表达不同记录类型。

**建议**

- 检查浅灰文字在白色和浅灰背景上的对比度。
- 危险操作不应因为“降低干扰”而变得难以识别。
- 状态同时使用文字、图形或位置，不只依赖颜色。
- 开启系统大字体进行布局检查。

**验收标准**

- 主要文字和操作在户外及低亮度环境仍清晰。
- 色觉差异用户仍可区分日历记录类型和库存状态。

---

### UX-08：删除操作缺少统一与撤销能力（P2）

**问题**

饮食记录、生活清单、库存和今日清单均有删除，但确认标题、按钮颜色和反馈方式不统一；批量删除明确不可撤销。

**建议**

- 统一危险操作文案和弹窗结构。
- 对记录类数据考虑软删除或短时间撤销。
- 清空今日清单与删除历史记录应采用不同风险等级。
- 异步删除失败时恢复原状态并提示。

**验收标准**

- 所有删除操作的对象和结果表达明确。
- 关键历史记录至少支持软删除、最近删除或撤销之一。

---

### UX-09：生活清单入口层级较深（P2，需观察真实使用频率）

**现状**

底部导航为“首页 / 饮食清单 / 记录”，生活清单只能从首页进入。

**影响**

如果生活清单成为核心能力，频繁返回首页会增加操作成本；如果饮食仍是绝对主场景，当前导航则可能合理。

**建议**

- 先通过使用记录判断饮食与生活清单的访问频率。
- 评估“首页 / 清单 / 记录”的场景化导航，让“清单”页同时容纳饮食和生活清单。
- 不建议仅凭页面数量调整 tabBar。

**验收标准**

- 高频任务从打开小程序到开始勾选不超过少量步骤。
- 用户不会把“饮食清单”误认为全部清单的入口。

---

### UX-10：首页概览需要可信状态（P2）

**位置**

- `pages/home/home.js`
- `pages/home/home.wxml`

**问题**

首页同时读取云端饮食清单和本地生活清单；任何加载异常都可能让概览数量显示为默认 0。

**建议**

- 云端与本地状态分别加载，单方失败不影响另一方。
- 在场景卡片上显示局部加载或失败提示。
- 如果以后迁移云端，应定义首页聚合接口，避免多次请求造成闪烁。

**验收标准**

- 云端失败时生活清单数量仍正常显示，反之亦然。
- 失败状态不伪装成“尚未创建”。

## 5. 推荐实施顺序

### 阶段 0：建立可验证基线

1. 固定稳定基础库版本。
2. 在微信开发者工具中完成一次无修改编译和主流程走查。
3. 增加最小静态检查和逻辑测试。
4. 记录当前数据库集合结构和测试账号数据。

### 阶段 1：处理安全和数据正确性

1. 关闭或保护 `reinit`。
2. 修复菜谱并发初始化。
3. 增加云函数输入校验和统一错误处理。
4. 实现饮食记录分页、按月查询及正确统计。

### 阶段 2：确定数据同步策略

1. 决定生活清单、库存和收藏是否云同步。
2. 设计数据模型、迁移和冲突解决方案。
3. 加入本地数据版本机制。

### 阶段 3：统一领域模型和工程结构

1. 清理价格和订单状态等遗留字段。
2. 分批重命名 cart/order 等旧术语。
3. 提取服务层、领域逻辑和可测试函数。
4. 删除确认无引用的遗留页面及样式。

### 阶段 4：设计系统与重点页面优化

1. 建立设计令牌和基础组件。
2. 先优化首页和记录页信息架构。
3. 统一加载、空、错误、确认和反馈状态。
4. 完成触控面积、安全区、字体放大及真机兼容检查。

## 6. 每个开发任务的完成要求

后续交给 Codex 时，建议每次都附上以下约束：

- 修改前先说明现状、目标、涉及文件和可能的数据兼容影响。
- 一次只处理一个风险编号或一组强相关问题。
- 保留用户已有数据，不直接清空云数据库或本地存储。
- 数据结构变化必须提供迁移和回滚方案。
- 运行项目已有检查；如果缺少检查，先补最小验证。
- 使用微信开发者工具编译并检查控制台错误。
- 涉及界面时至少验证空状态、正常状态、长内容、加载失败和大字体。
- 涉及云函数时至少验证未授权、非法输入、正常输入和重复调用。
- 完成后给出修改文件、验证结果、未验证项和推荐 commit 信息。

## 8. 建议的首个开发任务

建议先从 **R-01 菜谱重新初始化接口权限控制** 开始，因为它范围较小、验收明确，并且涉及潜在的全局数据破坏风险。

完成 R-01 后，再处理 R-02 和 R-03；不要先进行大规模 UI 重构。这样可以先保证数据安全和长期正确性，再在稳定基础上调整视觉与交互。
